# Tidy DS Toolbox - Comprehensive Project Audit

Audit date: 2026-08-03
Repository state: branch `main` at commit `8d7ec6c` (the branch `feat/release-notes-card-appearance` was merged into `main` while the audit was in progress; all file reads reflect committed code).

## 1. Executive summary

Tidy DS Toolbox is a Figma plugin suite for design-system maintenance, with a companion MCP server that exposes typed Figma operations to AI agents, and a self-hosted usage-analytics pipeline. The project is in active development. The release-notes, QA, and tidy-doc modules are recent, well-engineered, and heavily test-covered. The older modules (audit, ds-explorer, sticker-sheet-builder, off-boarding, component-labels, tidy-mapper) are largely untested.

Overall assessment: the project is healthy, unusually well documented for its size, and its recent architecture (Operations layer, ADRs, catalogue-driven QA) is a strong foundation. No critical vulnerability, no committed secret, and no imminent data-loss path was found. The main weaknesses are: an oversized UI bundle dominated by the icon database, a hand-maintained timeout allowlist, several untested destructive document operations, dead code from earlier refactors, and a release pipeline that uses a deprecated GitHub Action.

Most serious risks:

- The 5 MB UI bundle loads on every plugin start; 3.8 MB of it is the inlined icon database (62 %), and first use of Icon Finder blocks the UI thread for about 260 ms while it decodes 14 MB of JSON.
- The 30-second timeout does not stop the underlying operation. A timed-out document mutation keeps running and can change the file after the user was told it failed.
- The hand-maintained `LONG_RUNNING_ACTIONS` allowlist in `code.ts` silently times out any new slow action that nobody added to it.
- The shipped MCP server bundle contains `ws` 8.20.1, which has a known high-severity memory-exhaustion advisory. The vulnerable version is reachable on localhost from any local process.
- The ingest token is baked into every released plugin bundle, so the analytics endpoint is effectively protected by obscurity. There is no rate limiting.
- The six oldest modules have no unit tests, including the off-boarding pack/unpack flow, which deletes and recreates pages.

Main sources of technical debt:

- `tags-spacings`: a disabled module of about 3,955 lines still type-checked and maintained.
- Dead code: `searchIndexLegacy`, `withRetry`, `createShapeRectangles`, `insertText`, unused search helpers, unused `permissionRequirements` metadata.
- `deployment/` directory: tracked files that the deploy script regenerates, which dirties the working tree after every deploy.
- `deployment/README.md`: a stale copy of the root README.
- Duplicated QA check-id lists in three places, kept in sync by tests rather than by structure.

Main performance or workflow bottlenecks:

- UI bundle: 4.98 MB (gzip 3.3 MB); icon DB is 3.8 MB of it.
- MCP server bundle: 1.0 MB; plugin main thread bundle: 319 KB.
- Build time is good: UI 3.2 s, plugin thread 31 ms, 916 tests in about 2 s.
- Whole-file scans (find components, QA name lookup) are documented as expensive; page-scope is the recommended lever.

Confidence level: High for structural findings and measured performance; Medium for a few behavior-in-Figma claims (timeout continuation, plugin-data size limits) that cannot be verified without a live Figma session.

Findings that deserve attention first (see section 5 for details):

1. PERF-001 - Icon database dominates the UI bundle (62 %); measured 260 ms blocking decode.
2. REL-001 - Timed-out operations continue running and can still mutate the document.
3. REL-006 - The long-running action allowlist is hand-maintained and has no enforcement test.
4. SEC-002 - `ws` 8.20.1 with a high advisory ships inside the bundled MCP server.
5. REL-003 - `findReportFrame` mutates the user document from a read-only "check" path.
6. SEC-004 - Ingest token is extractable from any released bundle; no rate limiting.
7. TEST-001 - No tests for the six oldest modules, including destructive operations.
8. OPS-001 - `softprops/action-gh-release@v1` uses a deprecated Node 16 runtime.
9. DX-004 - `deployment/` regeneration dirties the working tree on every deploy.
10. ARCH-002 - `tags-spacings` is 3,955 lines of disabled, still-maintained code.

## 2. Project and architecture overview

### Purpose

Tidy DS Toolbox is a Figma plugin that bundles 12 design-system maintenance modules into one shell: DS Explorer, Component Labels, Tidy Icon Care, Sticker Sheet Builder, Tidy Mapper, Utilities, Audit, Release Notes, Off-Boarding, Icon Finder, Color Finder, and Tidy Doc. The project is being extended into an execution surface for AI agents: an MCP server exposes a curated set of typed Operations over a localhost WebSocket bridge to the plugin.

### Applications and packages

The repository is a single npm package plus two side packages, not a workspace:

- Root package `tidy-ds-toolbox` (version 1.17.1): the Figma plugin. Two build targets:
  - UI thread: React 19 app, Vite build, bundled into one self-contained `dist/index.html` (4.98 MB).
  - Plugin thread: Figma API code, esbuild build into `dist/code.js` (319 KB).
- `mcp-server/`: a Node MCP server (`@tidy/mcp-server`, private). Own dependency tree, installed via a root `postinstall`. Bundled into `dist/server.cjs` (1.0 MB) by `mcp-server/build.js`.
- `analytics-server/`: a Node/Express ingest service (`@tidy/analytics-server`) with its own dependency tree. Not part of the plugin build; deployed to a DigitalOcean droplet.
- `claude-plugin/`: canonical source of the Claude Code plugin (slash commands and skills).
- `scripts/`: release, deploy, dogfood, and generation scripts.
- `deployment/`: tracked folder that mirrors a released bundle (manifest, README, checksums).

### Technology stack

TypeScript 5.9 (strict) for the plugin and MCP server; React 19; Vite 7 + vite-plugin-singlefile; esbuild for the plugin thread and the MCP bundle; Vitest 4 for tests; ESLint 9 + Prettier; Zod 3 for MCP schemas and the Doc Spec; fflate and pdf-lib in the UI bundle; Express 4 + pg for the ingest service; Postgres 14 on the droplet; Metabase (local Docker) for dashboards.

### Data flows

- UI to plugin: typed `{ target, action, payload, requestId }` postMessage envelopes (`src/shared/bridge.ts`, `src/code.ts`).
- Plugin to UI: `{ type: "response" | "error" | ... }` messages with the same requestId.
- Agent to Figma: MCP stdio -> `mcp-server/src/server.ts` -> `BridgeServer` (WebSocket on 127.0.0.1:9876) -> plugin UI iframe (`UiBridge`) -> plugin main thread (`dispatch` in `src/shared/operations/registry.ts`) -> Operation handler -> reverse path.
- Analytics: plugin thread captures events (`src/shared/analytics/capture.ts`), relays to UI, UI batches and POSTs to `https://toolbox-logs.wearekido.dev/events`, nginx -> Express -> Postgres.

### Runtime boundaries and trust

- The Figma plugin sandbox has no network access except the single analytics origin listed in `manifest.json` `networkAccess.allowedDomains`. The dev bridge URL is under `devAllowedDomains`.
- The MCP bridge trusts any local process (documented in ADR-0005, accepted risk).
- The ingest service trusts the bearer token; the token is also baked into plugin builds.

### Storage

- Plugin settings in `figma.clientStorage` (active module, window size, bridge mode, per-module settings).
- Release-notes sprints and audit notes in shared plugin data on `figma.root` (survives file moves; visible to other plugins using the same namespace).
- Analytics events in Postgres (`events` table, schema v2, no client-identifying columns).
- Icon database: generated, committed `src/plugins/iconfinder/db/generated.ts` (gzip+base64 JSON).
- QA approved-asset manifest: committed `src/plugins/qa/asset-manifest.json` (currently empty; see REL-010).

### Build, test, and deployment workflow

- `npm run build` = Vite UI build + esbuild plugin-thread build.
- `npm run typecheck` covers `src/` and `mcp-server/`.
- `npm test` runs 916 Vitest tests across `src/` and `mcp-server/src`.
- CI (`.github/workflows/ci.yml`): lint, format check, unit tests on Node 20 and 24, typecheck, two MCP smoketests, build validation with a 6 MB bundle cap.
- Release (`.github/workflows/release.yml`): on tag push, runs CI, validates the tag against `package.json`, builds `plugin-bundle.zip`, creates a GitHub Release, and optionally publishes the Claude Code plugin to a distribution repo.
- Manual Google Drive distribution via `scripts/deploy-to-drive.sh`.
- Analytics deployment is documented as a runbook in `analytics-server/README.md`.

## 5. Detailed findings

### PERF-001 - Icon database dominates the UI bundle and blocks the UI thread

Classification: Performance; Severity: Medium; Confidence: Confirmed; Effort: M; Affected: `src/plugins/iconfinder/db/generated.ts`, `decode.ts`, `load.ts`, `moduleRegistry.ts`.

Evidence:
- `dist/index.html` is 4,980 kB (gzip 3,305 kB).
- esbuild metafile: `src/plugins/iconfinder/db/generated.ts` is 3,792 kB of the 6,141 kB of input bytes (62 %).
- Measured first-use decode (Node, same code path): base64 decode 164.6 ms, gunzip 73.3 ms, JSON.parse 19.7 ms, BigInt conversion 2.1 ms; total about 260 ms. Decompressed JSON is 14.0 MB for 22,414 icon entries (10.5 MB of SVG paths).

What is happening: every plugin start loads a 5 MB HTML file because the icon database is inlined as gzip+base64 in the single-file UI bundle. The decode is lazy, but the download and parse of the 5 MB HTML are not. The first Icon Finder use then synchronously decodes 14 MB and builds 22,414 `BigInt` hashes on the UI thread.

Why it matters: Figma plugin load time is a user-experience cost paid on every session, by every module user, even if Icon Finder is never opened. The measured 260 ms freeze happens on first icon search. The 6 MB CI cap is close to the current size, so the next icon-set addition can break CI.

Failure or abuse scenario: a designer opens the plugin for Release Notes; Figma must transfer and parse 5 MB first. Later, adding one more icon pack to the generator pushes the bundle past the 6 MB CI limit and the release pipeline fails.

Scope: Cross-cutting, user-facing, development-visible (CI cap).

Recommended direction: Move the icon database out of the UI bundle: lazy-load it via a second plugin entry (`figma.showUI` with dynamic HTML), or fetch it from a bundled asset on demand, or compress with a stronger scheme and decompress off the main thread. Keep the CI size cap.

Validation needed: measure plugin open time in Figma before and after; confirm the icon DB is only needed by Icon Finder; check Figma's plugin asset-loading rules for secondary bundles.

### REL-001 - A timed-out operation keeps running and can mutate the document after failure is reported

Classification: Reliability; Severity: Medium; Confidence: High; Effort: S; Affected: `src/code.ts:201-204`, `src/shared/error-handler.ts:35-58`.

Evidence:
- `withTimeout` races the handler against a timer (`Promise.race`). The losing promise is not cancelled.

What is happening: when the 30 s timeout fires, the UI receives an error, but the handler continues executing in the plugin sandbox. Document mutations started before the timeout still complete.

Why it matters: for build-like operations (sticker sheet, doc page, labels), the user sees "timed out" and may retry. Both the original and the retry then mutate the file, producing duplicates or double work. The error message does not say "the operation may still complete".

Failure or abuse scenario: on a slow machine, `tidy_component_labels_build` times out at 30 s; the user retries; the first run finishes after the retry, and two overlapping label sets appear.

Scope: User-facing, development-only (UI actions; MCP execute ops bypass via the bridge timeout), document-mutating.

Recommended direction: distinguish "cancelled" from "still running": log a warning when the handler settles after a timeout, and surface "may still be running" in the error text. For idempotent-by-stamp operations (release-notes, tidy-doc), verify stamps before drawing to make retries safe.

Validation needed: reproduce in a live Figma session with a deliberately slow operation; confirm the handler settles after the timeout fires.

### REL-002 - Audit handler loads fonts on every action

Classification: Reliability/Performance; Severity: Low; Confidence: Confirmed; Effort: XS; Affected: `src/plugins/audit/logic.ts:28-45`.

Evidence: `loadFonts()` awaits two `figma.loadFontAsync` calls at the top of `auditHandler`, before the action switch. It runs for `get-selection-state`, `check-report-exists`, `erase-report`, and `export-csv` too.

What is happening: every audit action, including read-only ones, awaits font loading for "Inter" Regular and Bold. If the font cannot be loaded, every audit action fails, including erase and export.

Why it matters: read-only actions pay a network-dependent cost; a font hiccup disables the whole module. Font loading is only needed where text nodes are created.

Failure or abuse scenario: Figma's font service is slow or "Inter" is unavailable in the session; the user cannot even check their selection state in the Audit module.

Scope: Local (audit module), user-facing.

Recommended direction: load fonts only in the actions that create text nodes, and handle font-load failure per action.

Validation needed: none beyond reading; the fix is a small move of the call.

### REL-003 - "Check report exists" mutates the user document

Classification: Correctness; Severity: Medium; Confidence: Confirmed; Effort: XS; Affected: `src/plugins/audit/logic.ts:404` (inside `findReportFrame`).

Evidence: `findReportFrame()` executes `reportFrame.layoutMode = "VERTICAL"` on every call. It is called from `handleCheckReportExists` (which the UI invokes on mount, `ui.tsx:53`), from both PDF exports, and from the CSV path.

What is happening: a read-only "does the report exist" query changes the layout mode of the user's report frame if it is not already VERTICAL.

Why it matters: the plugin changes the document as a side effect of a check the user did not ask to run. This is the class of behavior the QA engine itself forbids for agent operations (ADR-0001). It can visibly re-layout a report the designer arranged differently.

Failure or abuse scenario: a designer sets the report frame to HORIZONTAL to arrange sections side by side; opening the Audit module re-flows the frame to VERTICAL without any user action.

Scope: Local (audit module), user-facing, document-mutating.

Recommended direction: remove the assignment; if the report layout depends on VERTICAL, set it only when building or generating, not when checking.

Validation needed: confirm the UI relies on this side effect (search for layout assumptions in `audit/ui.tsx` and `buildReport.ts`).

### REL-004 - Off-boarding temp page cleared by name; unpack fallback moves the current page's frames

Classification: Reliability; Severity: Medium; Confidence: Confirmed; Effort: S; Affected: `src/plugins/off-boarding/logic.ts:10-34, 214, 227-260`.

Evidence:
- `TEMP_PAGE_NAME = "__TCC_TEMP__"`; `getOrCreateTempPage` treats any page with that name as the plugin's page, and `packPages` calls `clearPage(tempPage)`, which removes all children.
- `unpackPages` falls back to the current page when no temp page exists, then moves every top-level FRAME on that page into new pages.
- The UI (`off-boarding/ui.tsx:112-155`) triggers both with one click and no confirmation.

What is happening: pack deletes everything on any page named `__TCC_TEMP__` (the plugin's own page, but the name is not namespaced). Unpack, without a temp page, reorganizes the user's current page.

Why it matters: a designer who names a page `__TCC_TEMP__` for their own purposes loses its contents on pack. Unpack on the wrong page scatters its top-level frames into new pages. Undo helps, but the trigger is one click with no confirmation.

Failure or abuse scenario: a designer tests the flow: they pack, delete the temp page manually, then click unpack to restore. Every top-level frame on the current page is moved into new pages, some with duplicated names.

Scope: Local (off-boarding module), user-facing, document-mutating, data-related.

Recommended direction: namespace the temp page name, refuse to clear a page that carries no plugin marker, confirm before unpacking from a non-temp page, and store the packed page list in plugin data so unpack does not guess.

Validation needed: manual Figma test of pack/unpack cycles, including the delete-temp-page case.

### REL-005 - Sprint and note ids can collide

Classification: Correctness; Severity: Low; Confidence: Confirmed; Effort: XS; Affected: `src/plugins/release-notes/logic.ts:95, 150`.

Evidence: sprint ids and note ids are `Date.now().toString()`.

What is happening: two sprints (or notes) created in the same millisecond get the same id. Sprint ids are used as shared-plugin-data keys, so a collision silently merges two sprints into one stored blob.

Why it matters: automation or fast clicking can merge data with no error. Low probability for humans; real for scripted use.

Scope: Local (release-notes), data-related.

Recommended direction: use a counter or random suffix (the analytics session id already uses `Date.now().toString(36) + nonce`).

Validation needed: none; the fix is trivial.

### REL-006 - Hand-maintained long-running action allowlist

Classification: Reliability; Severity: Medium; Confidence: Confirmed; Effort: S; Affected: `src/code.ts:19-43`.

Evidence: `LONG_RUNNING_ACTIONS` is a `Set` of literal strings. No test checks that slow operations are listed. The list already missed at least two plausible slow actions (`audit:export-multipage-pdf`, `off-boarding:pack-pages`), which are not exempt and will hit the 30 s default on large files.

What is happening: any action not in the set is wrapped in the 30 s timeout. New slow actions must be added manually, and nothing fails when they are not.

Why it matters: a missed entry produces a confusing timeout on a legitimate operation; combined with REL-001, the operation may still complete after the error.

Failure or abuse scenario: a designer runs "Export multi-page PDF" on a 60-section report; each child export takes about a second, the 30 s cap fires, and the UI reports failure while the loop keeps running.

Scope: Cross-cutting (all modules), user-facing.

Recommended direction: invert the model: mark operations that are O(1) instead of an allowlist of slow ones, or register a per-action timeout in the module manifest, and add a catalogue test that asserts every known heavy operation is covered.

Validation needed: audit every handler for file-scaling work and compare against the set; verify `export-multipage-pdf` and `pack-pages` timing in Figma.

### REL-007 - Unbounded sprint blobs in shared plugin data

Classification: Reliability; Severity: Low; Confidence: Medium; Effort: S; Affected: `src/plugins/release-notes/utils/sprintHelpers.ts:34-41`.

Evidence: each sprint is stored as one `JSON.stringify(sprint)` value under `figma.root.setSharedPluginData`. Sprint size grows with note count and note length, with no cap or handling.

What is happening: Figma caps plugin-data values per key. A sprint with many long notes can approach or exceed the cap; the write then fails and the note is lost to the user's view (the error surfaces as a generic handler failure).

Why it matters: the data is user-authored release content with no backup path.

Scope: Local (release-notes), data-related.

Recommended direction: split notes into per-note keys, or compress, or enforce a per-sprint size limit in the UI with a clear message.

Validation needed: verify the actual Figma plugin-data size cap in a live session; measure a worst-case sprint.

### REL-008 - Icon Finder exports the full selection on every selection change

Classification: Performance; Severity: Low; Confidence: Confirmed; Effort: XS; Affected: `src/plugins/iconfinder/logic.ts:33-63`.

Evidence: `figma.on("selectionchange")` triggers `handleSelectionChange` with no debounce; it exports every selected node as a 64 px PNG immediately.

### SEC-007 - FNV-1a file hash

## 6. Performance analysis

### Measured bottlenecks

- UI bundle: 4,980 kB (gzip 3,305 kB); plugin-thread bundle 319 kB. The 6 MB CI cap leaves 1 MB of headroom. (PERF-001)
- Icon DB decode: 260 ms blocking (164.6 ms base64, 73.3 ms gunzip, 19.7 ms parse, 2.1 ms BigInt) plus 14 MB transient memory. Measured on a modern laptop; slower on typical design machines.
- Build: vite 3.2 s, esbuild 31 ms, MCP bundle 84 ms. Fast.
- Tests: 916 tests in 2.05 s. Excellent feedback loop.
- MCP smoketest: about 1 s. Good.

### Strongly inferred bottlenecks

- `auditHandler` font loads on every action (REL-002): network wait on read-only paths.
- Icon Finder selection exports without debounce (REL-008).
- Whole-file walks: `tidy_misprint_find_components` (scope=file), QA name/glob resolution (`loadAllPagesAsync` + `findAllWithCriteria`), tidy-doc related-candidate scan. All documented as expensive; all have page-scope or nodeId levers. The docs handle this well.
- `@tabler/icons-react` contributes about 970 kB of module input; tree-shaking trims the output, but the moduleRegistry imports icons individually from the barrel. If the bundle needs another 10 %, importing from the deep icon paths (or `@tabler/icons` direct) removes the barrel.

### Areas that require profiling

- Publish whole-file redraw on a file with hundreds of subjects.
- `tidy_doc_build_page` on a component with many variants (the mode cross-product is capped at 8, variants are not capped in the same way).
- `tidy_qa_build_checklist` with `includeContactSheet` (capped at 48 instances).
- Off-boarding pack on a multi-thousand-node page.

### Build and CI performance

- CI runs seven jobs; each runs `npm ci` with caching. The matrix jobs double on Node 20 and 24. Total CI time is dominated by dependency installs. Acceptable.
- `npm ci` installs two trees via postinstall; a lockfile-only change in `mcp-server/` triggers a full root install in CI.

### Figma-specific performance

- The plugin thread timeout (30 s) is the de-facto performance contract; the allowlist (REL-006) is the enforcement mechanism and it leaks.
- The bridge timeout (60-120 s per operation) is enforced at the MCP layer; the Figma-background-throttling caveat is documented in both the catalogue descriptions and CLAUDE.md.

### Database and backend performance

- Ingest: single multi-row parameterized INSERT per request, pool max 4, two indexes on the events table. Plenty for the expected volume (events per designer action).
- The views aggregate over the whole table with no retention policy; the `events` table grows forever. At the current scale this is fine; a retention decision should be made before the table reaches tens of millions of rows.

## 7. Security assessment

### Threat model

The system has three trust surfaces:

1. The Figma plugin, which runs on the designer's machine inside Figma's sandbox. Its network access is restricted to one analytics origin in production builds.
2. The MCP bridge on 127.0.0.1:9876, which trusts any local process (ADR-0005).
3. The analytics endpoint, which trusts a bearer token that is also embedded in every released plugin bundle.

### Trust boundaries

- UI iframe to plugin thread: trusted (own code), with no schema validation of payloads (many `payload as X` casts). This matches the project's risk profile: the only actors are the plugin's own UI and the bridge relay. The bridge relay validates nothing either; the MCP server's Zod schemas are the only runtime validation on the agent path.
- Plugin thread to ingest: bearer token + TLS. The token is a public constant in the client (SEC-004).
- Ingest to Postgres: least-privilege roles (`toolbox_ingest` INSERT-only, `toolbox_readonly` SELECT-only), documented in SQL.

### Authentication and authorization

- MCP bridge: none, accepted (SEC-003).
- Analytics: constant-time bearer compare, 1 MB body cap, batch cap 1000. No rate limiting, no per-sender identity.
- Figma: plugin uses `currentuser` permission for author names in release notes; no other auth.

### Sensitive data handling

- Analytics: schema v2 has no file names or raw file keys; the file identity is a client-side FNV-1a hash (SEC-007). The privacy amendment migration (03_privacy_drop_client_data.sql) purges old columns. This is well done.
- The `console.log("[usage]", ...)` in `capture.ts` writes every event (including session id and file hash) to the plugin console; harmless in practice.
- The audit and release-notes modules store user-authored content in shared plugin data; this content is visible to any other plugin using the same namespace on the same file. Namespaces are `tidy:...` / `tcc` - low collision risk.

### Figma-specific security

- No `eval`, no `new Function`, no dynamic code generation anywhere in `src/` or `mcp-server/`.
- Document mutations are the product's purpose; the destructive paths (off-boarding, clear-canvas, publish) use stamps or review flows, with the gaps listed in REL-004 and REL-009.
- The open-external-link path is the only scheme-sensitive sink (SEC-005).

### API security

- The ingest endpoint is the only public API. It is behind nginx with TLS, a 1 MB body cap, and a token gate. Missing: rate limiting, request logging, alerting (OPS-004).
- The Figma REST API is only called by local generation scripts with a personal access token from the environment, never committed.

### Dependency and supply-chain risk

- Root: 9 advisories, all build-time (SEC-001). Fix is a routine update.
- mcp-server: 6 advisories; only `ws` reaches the shipped bundle (SEC-002). The hono and express code from the MCP SDK is tree-shaken out (verified).
- analytics-server: 1 low (body-parser via express 4); the app sets an explicit limit, so the advisory's trigger (invalid limit value) does not apply.
- CI actions are pinned to major versions, not SHAs; one uses a deprecated runtime (OPS-001).
- No secrets were found in git history (full-history scan); the only token-like values are environment references in READMEs and the CHANGE_ME placeholders in SQL.

### Operational security

- The systemd unit is well hardened (NoNewPrivileges, ProtectSystem, MemoryMax 150M).
- The env file is root-owned mode 600; the runbook says so.
- The deploy runbook documents real incidents (nginx include trap, certbot loop, pg_hba) with fixes. This is a strong positive.

### Confirmed vulnerabilities

- SEC-002 (`ws` in the shipped bundle) is the only advisory that reaches a distributed artifact, and its impact is local DoS.
- No exploitable injection, no secret exposure, no privilege escalation found.

### Risks requiring additional testing

- Whether the Figma plugin-data size cap can be hit by large sprints (REL-007).
- Whether a timed-out operation's late mutations can corrupt stamped artifacts (REL-001 + REL-009).

## 8. Architecture and maintainability assessment

### Package boundaries

Three dependency trees with a deliberate import seam between the plugin and the MCP server (ARCH-004). The seam is guarded by tests and a dedicated CI job. The plugin itself has a clean three-layer split: shell (`src/`), modules (`src/plugins/*`), shared (`src/shared/`).

### Coupling

- `moduleRegistry` is the hub for UI modules; `moduleHandlers` for the plugin thread; the Operations registry for agent operations. Three registries with three shapes - a deliberate historical layering, but new modules must register in all of them (registry, handlers, operations, catalogue, commands). The catalogue drift is guarded by `agent-surface.test.ts`.
- The QA engine is the model citizen: figma-touching code is confined to `collector.ts`, `theme-probe.ts`, `resize-probe.ts`, and the render layer; everything else is pure and fixture-tested. This is the pattern the older modules should follow.

### Duplication

- `CHECK_IDS` exists in three places (catalogue, `agent-surface.test.ts`, `/tidy-qa` command), kept in sync by tests.
- The README is duplicated in `deployment/` (DX-004).
- `temp/` holds a parallel release-notes copy (DX-005).
- `buildAutoLayoutFrame` exists in both audit and tidy-mapper utils; `buildHeaderFrame`/`addSectionTitle` in audit report; the sticker-sheet and tags-spacings share nothing despite similar purposes.

### State management

- Shell state via React reducer with postMessage side effects inside the reducer (ShellContext). Side effects in a reducer are unusual and can double-fire under React StrictMode (the dev build mounts twice, which is why the restore path is carefully idempotent).
- Analytics session id is module-scope state, correctly reset for tests.
- The Operation Session is a single global; switching files kills it (documented).

### Type safety

- Strict mode everywhere; `any` is a warning, with 173 lint warnings accumulated (0 errors). The warnings concentrate in `shared/types.ts` (message envelope types), `bridge.ts`, and `error-handler.ts`.
- Many `payload as X` casts at module boundaries (light-agent inventory: about 26 sites across logic files). The MCP catalogue path validates with Zod; the UI path validates nothing. Consistent with the trust model, but it means a UI bug can pass wrong shapes into Figma calls.

### Error handling

- Uniform error contract for Operations (ADR-0003); `code.ts` distinguishes recoverable errors and notifies the user.
- `withRetry` exists and is unused (ARCH-001); the QA code uses explicit sweep-and-retry patterns instead.
- Empty catch blocks are rare (one found in `lockStickers.ts:26`).

### Configuration

- Build-time configuration via Vite `define` (version, ingest endpoint, token) and esbuild `define` (version only). Environment variables: `TIDY_INGEST_TOKEN` (build), `FIGMA_TOKEN` (asset manifest), `TIDY_BRIDGE_HOST/PORT` (MCP server), `PORT/DATABASE_URL/INGEST_TOKEN` (ingest). Documented in the relevant READMEs.
- The token build flow means dev builds silently ship without analytics - a deliberate and well-documented design.

### Legacy areas

- `tags-spacings` (ARCH-002), `searchIndexLegacy`, the parked vertical doc layout (mentioned in CONTEXT.md as parked behind a constant), `tsconfig.main.json` (ARCH-005), and `temp/` (DX-005).

### High-risk modules

- Off-boarding (destructive, untested): REL-004.
- Audit (document mutation on read path, untested): REL-002, REL-003.
- Release-notes publish (whole-file redraw): REL-009.
- The QA probes (transient document writes in a read-only operation): the residue guarantee is the most carefully engineered safety property in the repo (theme-probe tests, stray sweep).

### Simplification opportunities

- Replace the hand-maintained long-running allowlist with a per-manifest timeout (REL-006).
- Remove the dead exports (ARCH-001).
- Move the icon DB out of the UI bundle (PERF-001).
- Consolidate the two READMEs (DX-004).
